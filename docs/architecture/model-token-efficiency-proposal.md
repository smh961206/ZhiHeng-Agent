# M1.1 模型 Token 效率优化具体方案

状态：规划稿
适用基线：V5.2 核心能力 + M1.0 按研究环节配置模型
计划轨道：M-Series，不占用已经分配给 Knowledge Engineering 的 V5.3 版本

## 1. 目标

在不削弱证据、计算、缺口披露、独立审计和断点恢复的前提下，减少模型重复接收的规则、原文、工具记录和修正历史。

目标不是限制研究可以使用多少 Token，也不按价格改变模型。平台继续执行完成研究所必需的取证和复核；优化只改变“每个环节收到什么上下文”和“相同内容是否重复发送”。

计划目标：

| 指标 | 目标 | 约束 |
| --- | --- | --- |
| 每份已验证交付的模型输入 Token 中位数 | 降低 30% 以上 | 包含失败调用和重试，不能只统计成功调用 |
| Writer 输入 Token 中位数 | 降低 40% 以上 | 报告引用、计算依据和缺失清单不能减少 |
| Auditor 输入 Token 中位数 | 降低 35% 以上 | 最终报告必须完整复核 |
| Researcher 输入 Token 中位数 | 降低 25% 以上 | 不能减少必要工具、反证或原文读取 |
| Vision 调用页数 | 不增加 | 仍只读版面、图片、扫描和歧义页 |
| 模型调用次数和重试次数 | 不增加 | 不能用更多小调用掩盖 Token 增长 |
| 确定性验证通过率 | 不下降 | 引用、财务口径、期间、来源和交付校验保持原规则 |

这些数值是发布目标，不是预先承诺的实际结果。实际 Token 只采用供应商返回的用量；未知值保持未知。

## 2. 当前实现与主要问题

当前系统已经具备以下基础：

- `server/evidence-search.mjs` 按稳定的 `sourceId + blockId` 返回完整证据块；
- `server/research-context.mjs` 按引用、计算依据和来源均衡顺序打包完整记录；
- `server/agent-execution.mjs` 在消息约 220000 字符后压缩研究上下文；
- `server/model-cache.mjs` 记录稳定系统前缀的缓存指纹；
- `server/model-telemetry.mjs` 按 Input、Vision、Researcher、Writer、Evidence Verifier、Auditor、Critical Reviewer 和 Judge 记录供应商实际 Token；
- Writer、Auditor、关键复核和 Judge 已有独立上下文及恢复边界。

主要问题：

1. Researcher 在压缩阈值前持续携带完整对话、工具参数和工具返回。
2. 已完成计算、失败记录和相同来源片段会在多轮对话中重复发送。
3. Writer 和 Auditor 都会取得较大的通用证据窗口，虽然两者所需信息不同。
4. 修正轮通常同时携带旧审计回复、完整报告、补证结果和再次构造的证据窗口。
5. 稳定规则会因拼接顺序或动态内容位置变化降低供应商前缀缓存命中机会。
6. 当前费用页面能按环节显示调用与缓存，但没有直接显示“每份交付”和“每次审计”的 Token 效率。

## 3. 不允许改变的研究质量边界

任何 Token 优化都必须满足：

1. 报告引用的每个来源都能定位到本次任务实际保存的来源。
2. 关键计算继续携带真实输入、输出、期间、币种、股本口径及 `sourceId + blockId`。
3. 原文表头、单位、期间、负号、脚注和行列关系不能被模型摘要替代。
4. OCR 与 Vision 内容继续标记为待核实，不能独立成为财务计算依据。
5. 未读取、未纳入窗口、失败和冲突内容继续作为缺口，不得自动变成已核实。
6. 反证和失败记录不能因为排序或压缩被静默删除。
7. Auditor 继续独立检查完整最终报告，不能只看 Writer 的修改摘要。
8. Critical Reviewer 和 Judge 仍只由 V5.2 的业务条件触发，不能为了节省 Token 跳过，也不能因为上下文较短而更频繁触发。
9. 恢复任务沿用原研究截止日期、模型身份、证据和已完成工具收据。
10. 隐藏推理、提示词正文、密钥和原始图片不进入公开执行轨迹或 Token 统计记录。

## 4. 目标流程

```text
Input
  只接收问题文本和必要证券候选
    ↓
Researcher
  稳定规则前缀 + 当前研究状态 + 按需证据块 + 精简工具收据
    ↓
Evidence Verifier
  只接收未解决检查项 + 涉及的原文块 + 对应计算
    ↓
Writer
  初稿 + 已引用证据 + 成功计算 + 反证 + 缺失清单
    ↓
Auditor
  完整最终报告 + 引用清单 + 计算依据 + 缺口 + 定向证据
    ↓
符合资格时才进入 Critical Reviewer / Judge
```

所有完整来源、工具结果、模型收据和检查点仍保存在现有后端。上下文投影只决定本次模型请求携带的内容，不成为新的事实来源。

## 5. 各环节的具体输入合同

### 5.1 Input

保留：

- 用户问题；
- 已由程序提取的证券候选及歧义；
- 六类研究路径名称和必要输出约束。

不发送：

- 财报正文；
- 历史执行轨迹；
- 组合详细信息；
- 后续研究工具定义。

现有 `/api/research/path` 已接近目标，只需保证动态问题位于稳定系统前缀之后，并继续使用 400 输出 Token 的技术上限。

### 5.2 Vision

只在以下情况读取：

- 扫描页没有可靠原生文字；
- 表格版面、图表、脚注或行列关系无法由程序确定；
- Auditor 指定的关键数字需要原页复读。

每次请求只带当前页及必要裁剪，不附带整份报告的研究对话。程序文本、页码、图片哈希和读取原因作为最小文字上下文。现有页数、图片大小和超时上限保持不变。

### 5.3 Researcher

每轮上下文拆成四部分：

1. **稳定规则前缀**：投资研究原则、工具协议、当前模式规则；
2. **任务状态**：问题、研究路径、公开计划、证券和数据截止日；
3. **本轮证据**：模型当前步骤所需的完整证据块；
4. **工具收据**：已完成结果的精简投影和仍未解决的错误。

每轮完成工具调用后，不继续携带所有旧工具消息。程序把已确认的结果合并进任务状态；只有仍与当前步骤相关的记录进入下一轮。

精简工具收据至少包含：

```json
{
  "toolName": "calculate_valuation_snapshot",
  "toolCallId": "call-123",
  "status": "completed",
  "result": {},
  "basis": {
    "period": "2025FY",
    "currency": "CNY",
    "shareBasis": "A股价格等值",
    "sourceIds": ["S2", "S5"],
    "evidenceBlocks": [
      {"sourceId": "S2", "blockId": "page-86-table-1"}
    ]
  }
}
```

`result` 只允许工具自己的公开结果字段。完整参数、失败详情和原始记录仍保存在 `toolRecords`，需要修正或审计时按 `toolCallId` 重新投影。

### 5.4 Evidence Verifier

输入从“通用研究上下文”改为“检查包”：

- 检查编号及失败原因；
- 报告中涉及的原句；
- 该检查引用的完整证据块；
- 相关计算收据；
- 当前仍未解决的 F/G 缺口。

一次检查不得带入无关来源。检查成功只更新对应检查项，不宣称其他资料已复核。

### 5.5 Writer

Writer 接收：

- Researcher 初稿；
- 初稿实际引用的完整证据块；
- 成功计算及其指定依据；
- 与结论相反的有效证据；
- 数据覆盖、研究截止日和缺失清单；
- 报告结构和交付规则。

Writer 不接收：

- Researcher 的完整消息历史；
- 已成功工具调用的重复自然语言说明；
- 与报告没有引用、计算或反证关系的普通证据块；
- 隐藏推理。

如果初稿引用的依据没有进入 Writer 上下文，程序停止 Writer 请求并要求重新构造上下文，不能让模型在缺证据时继续润色。

### 5.6 Auditor

Auditor 必须收到完整最终报告，但证据按以下顺序选择：

1. 报告实际引用的证据块；
2. 成功计算明确使用的证据块；
3. 与核心结论相反的证据；
4. 尚未解决的缺口和失败记录；
5. 其他来源只提供目录，需要时定向读取。

Auditor 不重复接收 Researcher 的对话历史。修正轮只附加：验证错误列表、发生变化的报告章节、新取得证据和受影响计算；最终 Auditor 请求仍包含修改后的完整报告。

### 5.7 Critical Reviewer 与 Judge

继续使用 `buildIndependentContext` 的完整性要求，不对其进行一般性摘要。只优化两点：

- 删除重复出现的相同证据块和相同工具收据；
- 固定规则前缀，将独立上下文放在最后的动态消息中。

如果完整独立上下文超过模型安全窗口，保持失败并保留原研究，不通过裁剪证据继续执行。

## 6. 上下文选择算法

在现有 `buildResearchContext` 上增加 `purpose` 和 `required`，不创建第二套证据系统。

候选记录按以下规则分类：

| 等级 | 内容 | 处理方式 |
| --- | --- | --- |
| R0 必须 | 报告引用块、计算指定块、反证、未解决缺口 | 完整纳入；不能容纳则停止请求 |
| R1 高 | 当前计划步骤、当前验证错误直接关联的证据和工具 | 完整纳入；必要时要求定向补读 |
| R2 中 | 同一来源的辅助背景、已完成但未引用的有效计算 | 有空间时完整纳入 |
| R3 目录 | 其他已保存来源和工具 | 只提供安全元数据和稳定编号 |

算法要求：

1. 先按 `sourceId + blockId` 和 `toolCallId` 去重；
2. R0 记录进行完整性预检；
3. 比较研究继续按来源轮转，避免一个长报告挤掉其他公司；
4. 不截断 JSON、表格或工具结果；
5. 超出窗口的 R1/R2 进入 `omittedEvidence` 或 `omittedTools`；
6. 模型只能按稳定编号请求缺失记录；
7. `calculationEvidence` 继续报告计算依据是否真正进入窗口；
8. 任何 R0 缺失都不能被描述为“模型已经看过”。

字符数只用于跨供应商的保守安全检查，不冒充 Token 数。实际 Token 来自供应商响应。

## 7. 稳定前缀与缓存

按以下顺序构造请求：

```text
固定系统规则
→ 固定工具定义
→ 固定输出结构
→ 当前研究模式规则
→ 动态任务状态
→ 动态证据和工具收据
```

要求：

- 动态日期、证券、问题和证据不能混入稳定系统前缀；
- 同一环节的工具顺序和 JSON Schema 字段顺序保持稳定；
- 不为了提高缓存命中而复用其他任务的用户内容或证据；
- 缓存统计继续以供应商实际返回的 `cachedInputTokens` 为准；
- 缓存命中不能成为证据可信度、模型质量或路由条件。

## 8. Token 观测与页面展示

复用现有 `ModelCall` 用量记录，不新增价格或预算配置。

费用页面增加只读效率指标：

- 本任务输入、输出和缓存输入 Token；
- 按八个环节分组；
- 每次调用平均输入 Token；
- 每份已验证交付的总 Token；
- 未返回 Token 用量的调用数；
- 相比同一路径、深度和模型的历史中位数变化。

比较只使用相同模型连接身份、研究路径、深度和版本的数据。样本不足时显示“样本不足”，不显示虚假节省比例。金额仍由可选价格表计算；没有价格不影响 Token 指标。

建议给 `ModelCall` 增加可选的私有安全元数据：

```json
{
  "contextStats": {
    "version": 1,
    "evidenceIncluded": 8,
    "evidenceOmitted": 2,
    "toolsIncluded": 5,
    "toolsOmitted": 1,
    "requiredComplete": true,
    "serializedCharacters": 28340
  }
}
```

该字段不保存提示词、证据正文、工具结果或隐藏推理。旧记录没有此字段时保持未知。

## 9. 实施分段

### M1.1.0：建立基线

- 固定当前按环节 Token 汇总口径；
- 将失败调用、重试和未知用量纳入分母；
- 记录同一路径、深度和模型的历史中位数；
- 不改变任何模型请求。

### M1.1.1：统一上下文投影

- 扩展 `buildResearchContext` 支持环节和 R0–R3 选择；
- 保持完整记录打包、来源均衡和计算依据校验；
- 增加必需记录缺失时的关闭式失败。

### M1.1.2：Researcher 增量上下文

- 工具轮结束后将旧消息替换为任务状态和精简收据；
- 从“达到 220000 字符才整理”调整为每个安全工具边界都可整理；
- 未返回的工具调用存在时禁止整理；
- 检查点继续保存恢复所需的完整私有状态。

### M1.1.3：Writer 专用上下文

- 只提供初稿引用、计算依据、反证和缺口；
- 加入 Writer 请求前完整性检查；
- 保留完整 Markdown 草稿和原有交付结构。

### M1.1.4：Auditor 与修正轮增量化

- 首轮审计接收完整报告和定向证据；
- 修正轮发送错误、变更章节和新增证据；
- 每轮仍运行完整确定性校验；
- 最终审计仍检查完整最终报告。

### M1.1.5：稳定前缀与缓存整理

- 固定规则、工具和 Schema 顺序；
- 将动态内容移至后缀；
- 验证请求语义、Gateway 身份和恢复哈希没有意外变化。

### M1.1.6：Vision 定向读取复核

- 检查选择页是否只覆盖扫描、版面歧义、图表和指定核对；
- 对重复页和相同原件哈希去重；
- 不改变 Vision 的证据等级及页数安全边界。

### M1.1.7：效率页面与发布验收

- 页面增加按环节 Token 和缓存统计；
- 使用正常研究产生的供应商用量做版本前后顺序比较，不建立 A/B、Champion 或付费试跑配置；
- 达不到质量门槛时整体回滚对应子版本。

## 11. Schema、迁移与兼容

如果增加 `ModelCall.contextStats`，采用可选加法字段：

1. 旧记录缺失时按未知读取；
2. 新代码只写安全计数，不写正文；
3. 不批量回填历史记录；
4. API 只返回白名单聚合值；
5. 旧前端忽略新增字段；
6. 回滚代码后 MongoDB 中的可选字段不会影响旧读取。

研究任务、证据、计算、报告和 modelState 不需要结构迁移。上下文算法版本如需保存，只作为私有检查点的可选字段加入；旧任务继续按创建时版本恢复，不能在恢复中途切换投影算法。

## 12. 验收门槛

### 12.1 硬性质量门槛

以下任一项失败即不能发布：

- 全量测试、发布专项、Mongo 集成和前端构建失败；
- 引用有效性、正文引用、期间、币种、股本或计算依据测试退化；
- R0 必需证据或反证被遗漏；
- 未解决缺口数量减少但没有新增证据或人工决定；
- OCR/Vision 被提升为已验证财务事实；
- Auditor 没有收到完整最终报告；
- 断点恢复重复执行已完成工具或模型调用；
- 公开 API、事件或页面泄露提示词、证据正文、隐藏推理或密钥。

### 12.2 效率门槛

按相同模型连接身份、研究路径、深度和代码版本分组：

```text
每份已验证交付 Token
= 该任务全部模型调用的 inputTokens + outputTokens
  ÷ 已通过确定性校验并成功交付的任务数
```

要求：

- 输入 Token 中位数达到对应子版本目标；
- P95 总 Token 不得增加超过 5%；
- 调用次数、失败率和重试次数不得上升；
- 缓存 Token 只在供应商返回可靠值时统计；
- 未知用量不得按 0 处理；
- 没有足够同类正常任务时结论保持“样本不足”。

### 12.3 质量等价检查

不恢复付费试跑、模型验收文件、Champion 或 A/B。质量检查分为：

1. 冻结资料和合成模型响应的离线回归；
2. 上下文清单的确定性完整性比较；
3. 现有引用、计算、审计和交付验证；
4. 正常研究产生的只读 Token、失败率和交付率观察。

这能证明平台没有程序性删除关键资料，但不能在不运行目标模型的情况下宣称模型语言质量绝对相同。因此发布必须按子版本逐步实施，每一步都可独立回滚。

## 13. 重点测试

- 相同引用和计算依据在优化前后全部存在；
- 多公司比较按来源轮转，不能被第一家公司挤出窗口；
- 同一来源重复片段和同一工具收据只出现一次；
- 长表格、JSON 和工具结果不被截断；
- R0 超过安全窗口时停止并报告缺口；
- 工具调用尚未返回时不压缩消息；
- Writer 缺少初稿引用块时不发起调用；
- Auditor 始终接收完整最终报告；
- 修正轮保留所有独立错误和未解决 F/G 编号；
- Critical Reviewer/Judge 完整上下文失败时不降级裁剪；
- Windows 进程退出、Mongo 重连和任务恢复不重复模型调用；
- Token 未知、缓存未知和价格未知分别保持未知；
- 公共费用接口不返回提示词、证据文本和私有检查点。

## 14. 配置变化

本方案不增加用户配置项。

继续使用：

- `MODEL_CONFIG_FILE`：模型和八个环节分配；
- `MODEL_TELEMETRY_ENABLED`：是否记录安全调用元数据；
- `MODEL_PRICING_FILE`：可选费用估算。

不恢复：

- 研究预算文件或预算开关；
- 每环节 Token 配额；
- MAIN/PRO、Challenger、Champion、A/B；
- 付费试跑和模型验收文件；
- 按价格自动路由。

## 15. 风险与处理

| 风险 | 处理 |
| --- | --- |
| 摘要丢失表格语义 | 关键证据只传完整块，不让模型摘要替代原文 |
| Auditor 上下文过短 | R0 完整性检查；无法容纳时停止，不静默裁剪 |
| 更频繁的小调用抵消节省 | 以每份交付的全部调用统计，不只看单次请求 |
| 缓存命中导致错误乐观 | 只读供应商实际缓存用量，未知保持未知 |
| 新算法破坏恢复 | 将投影版本固定到任务检查点，旧任务继续原路径 |
| 多公司证据不均衡 | 延续按来源轮转并增加每个标的最低 R0 覆盖检查 |
| 反证被相关性排序排除 | 反证属于 R0，必须完整纳入 |
| Token 下降但交付质量下降 | 硬性质量门槛优先，效率达标不能覆盖任何质量失败 |

## 16. 回滚

每个 M1.1 子版本独立提交。回滚时：

1. 恢复上一个上下文投影版本；
2. 保留全部任务、证据、计算、报告、ModelCall 和可选 `contextStats`；
3. 不修改历史研究截止日、模型身份或调用收据；
4. 已经用新投影创建并进入执行的任务由兼容代码继续恢复；
5. 不通过删除检查点强制重跑模型；
6. 重新执行全量、发布、Mongo、恢复和页面回归。

## 17. 推荐实施顺序

先完成 M1.1.0 基线与 M1.1.1 上下文完整性，再实施 Researcher、Writer 和 Auditor。缓存与页面统计放在上下文稳定之后，避免把尚未稳定的请求指纹当作长期基线。Vision 最后单独复核，因为它的图片、页码和证据等级约束与文本上下文不同。

第一批实际开发建议只做 M1.1.0–M1.1.3。通过所有硬性门槛后，再进入 Auditor、缓存与 Vision 优化。

跨任务、跨期间和财报更新的安全复用不属于 M1.1，后续由 [M1.2 增量研究与依赖图方案](model-incremental-research-proposal.md) 负责。
